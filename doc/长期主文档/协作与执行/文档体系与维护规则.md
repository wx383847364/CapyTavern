# 文档体系与维护规则

本页说明 CapyTavern 的文档怎么分区、放在哪、由谁写、什么时候更新。

## 1. 分区

| 位置 | 放什么 | 唯一写者 | 进 git |
|---|---|---|---|
| `doc/长期主文档/项目总览.md` | 项目定位、当前阶段、稳定结论 | 制作人 | 是 |
| `doc/长期主文档/主文档索引.md` | 研发入口页、阅读路径、文档分区 | 制作人 | 是 |
| `doc/长期主文档/架构与边界/` | 分层、目录、写权、引擎与热更边界 | 制作人 | 是 |
| `doc/长期主文档/方案与数据/` | 已裁决、已验收的稳定方案 | 制作人 | 是 |
| `doc/长期主文档/协作与执行/` | 提交规则、文档规则、验收与协作流程 | 制作人 | 是 |
| `doc/方案与数据/` | 草案、版本迭代、数值与原型 | 策划、制作人 | 是 |
| `doc/迭代记录/` | 每轮工作记录与索引 | 制作人 | 是 |
| `doc/裁决.md` | 跨层争议、契约变更、白名单冲突，一条一行 | 制作人 | 是 |
| `doc/软著申请/` | 软著材料，等需要时再建 | 制作人 | 是 |
| `locks.md` | 写锁台账 | 调度台 | 否 |
| `dispatch.md` | 派发、交接、阻塞台账 | 调度台 | 否 |

写权以 `TEAM.md` §2 为准；本页与之冲突时，先改 `TEAM.md`，再同步本页。

## 2. 草案到稳定

1. 新方案先落在 `doc/方案与数据/`，文件名用 `主题 vX.Y.md`。
2. 同主题升级版本时另起文件，不覆盖旧版；旧版保留追溯。
3. 每份草案开头写清：

```text
> 状态：草案 / 评审中 / 已稳定
> 版本：v0.1
> 更新：2026-11-04
> 负责人：酒馆策划
```

4. 经过制作人裁决或验收后，复制稳定版到 `doc/长期主文档/方案与数据/`，改状态为「已稳定」，并在 `主文档索引.md` 登记。
5. 稳定版只改结论和日期，不悄悄改历史版本；草案不再回写。

## 3. 迭代记录

什么时候写：

- 工程级改动（新增模块、改目录、接引擎、改构建）。
- 跨岗交接、契约变更、重要裁决。
- 项目阶段或主线变化。

不用写：错字、纯格式、单条链接修正。

怎么写：

1. 复制 `doc/迭代记录/_模板.md`。
2. 文件名：`迭代记录_YYYYMMDD_NNN.md`，当天从 `001` 起。
3. 至少填：目标、完成、验证、风险与阻塞、下一步。
4. 更新 `doc/迭代记录/迭代记录索引.md` 的总数、最新记录、最近完成、最新阻塞、下一步和记录清单。
5. 阶段变化时，同步 `项目总览.md`。

## 4. 索引维护

`主文档索引.md` 是研发入口页，不是普通目录：

- 当前阶段变化：先改「当前概览」。
- 稳定边界变化：先改「稳定决策速览」。
- 新增长期文档：补「文档分区」和「最近更新」。
- 阅读路径只在入口变化时改，不追每个小改动。

## 5. 写权与锁

- 动手改 `client/`、`design/`、`server/`、`protocol/`、`doc/` 前，先看 `locks.md`。
- 同一目录同一时刻只允许一个写者。
- 交接前核对 `git status` 与 `git diff`，保留对方原有改动。
- 调度台只维护 `locks.md`、`dispatch.md`；human 直接指派时可以代写文档，写完交回制作人确认。

## 6. 工具

`tools/doc_maintenance/**`、`tools/repo_maintenance/**`、`.githooks/**` 的唯一写者是酒馆制作人。

| 工具 | 用途 |
|---|---|
| `tools/doc_maintenance/next_commit_id.py` | 按模块取下一个八位编号 |
| `tools/doc_maintenance/check_commit_message.py` | 校验提交标题；hook 和手工都用它 |
| `tools/repo_maintenance/install_git_hooks.sh` | 安装 `.githooks`，设置 `core.hooksPath` |

以后客户端构建或资源管线脚本放 `tools/client/**`，写者改为酒馆程序，并先改 `TEAM.md` §2。

## 7. 暂不自动化

文档量还小，先手动维护索引和迭代记录。等出现以下情况再考虑脚本：

- 长期文档超过 30 份，手工找漏开始频繁。
- 迭代记录超过 20 份，索引维护明显耗时。
- 多人同时改文档，手工合并索引开始冲突。

现在只保留提交编号和提交信息校验两个脚本，避免工具比文档本身还重。
